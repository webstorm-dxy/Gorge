# Native 类桥接 ID 对齐规则

> Step 0 产出物。目的：在实现 `GorgeMacros` proc-macro 之前，厘清 Rust 编译器
> （`GorgeCompiler`）生成 IR 时使用的 method / constructor / field / injector 编号
> 与 index 的分配规则，对照 C# 参考实现（`AutoGenerated/`），给出宏必须遵守的
> 对齐规则，避免宏生成的桥接层与编译器产出的 IR 指令“错位”。

---

## 1. 结论速览

Rust 编译器当前的编号方案与 C# 参考实现存在 4 处**不一致**，宏不能照搬 C#，
必须以 **Rust 编译器当前实际生成的 IR 为准**。核心对齐点：

| 维度 | C# 参考实现 | Rust 编译器现状 | 宏应遵守 |
|------|------------|----------------|----------|
| 静态方法编号 | 静态方法独立编号（`staticMethods[]` 下标） | `class_info.methods`（静态+实例**混合**列表）的 enumerate 下标 | **混合列表下标** |
| 实例方法编号 | `methods[]` 下标 + `MethodStartId` 继承偏移 | 同上混合列表下标，`method_start_id=0` | **混合列表下标** |
| 字段 index | 按值类型**分组**计数（float:0, float:1） | 全类型**统一**递增（0,1,2…） | 见 §4，需专门处理 |
| 继承编号冻结 | `MethodStartId`/`MethodOverrideId` 实现 | 全部置 0 / 空，**未实现** | 示范类无继承，暂回避 |

> 由于本轮示范类 `Math`、`Vector2` **均无父类、无继承**，继承编号冻结（§5）暂不影响，
> 但字段 index（§4）与静态方法编号（§2）必须严格对齐。

## 2. 方法 / 静态方法编号

### 2.1 编译器实际逻辑

`codegen.rs::generate_method_call`（第 609-708 行）解析 `ClassName.method(args)`：

```rust
let class_info = self.symbol_table.classes.get(class_id.0);
for (i, &method_id) in class_info.methods.iter().enumerate() {
    let mi = self.symbol_table.methods.get(method_id.0);
    if mi.name == method && mi.is_static {
        // idx = i  →  InvokeStatic(i)
    }
}
```

- `class_info.methods` 是一个 **`Vec<MethodId>`**，由 `symbol.rs::declare_method`
  在 Pass 3 **按源码声明顺序** push（静态方法、实例方法**混在同一个 Vec**）。
- `InvokeStatic(idx)` / `InvokeInstance(idx)` 的 `idx` = 方法在这个混合 Vec 里的**枚举位置**。
- `method_start_id` 恒为 0（`vm_main.rs` / `main.rs` 都写死 0）。

### 2.2 VM 侧消费逻辑

`vm.rs::InvokeStatic(idx)`（第 977 行）：

```rust
let methods = self.class_static_methods.get(&self.current_class)?;
let (static_method, _) = methods[*idx].clone();
```

而 `class_static_methods` 由 `vm_main.rs`（第 123-126 行）填充：

```rust
for method in &compiled_class.methods {   // 与编译期同一个混合顺序
    method_params.push((method.clone(), vec![]));
}
vm.register_class_methods(&class_name, method_params);
```

即 VM 的方法表就是 `compiled_class.methods`，**顺序与编译期 `class_info.methods` 一致**
（都来自符号表声明顺序）。因此编译期 `idx` 与运行期 `methods[idx]` 自洽。

### 2.3 宏对齐规则

> **规则 M1**：native 类的方法（含静态与实例）必须放进**同一张有序方法表**，
> 顺序 = 源码/宏声明顺序。桥接层的 `invoke`（静态与实例合一）用**同一编号空间**的
> `switch(method_id)` 分派，`method_id` 即该表下标。
>
> **规则 M2**：不要采用 C# 那种“静态方法独立编号 + 实例方法独立编号”的双编号空间。
> Rust 侧是单一混合编号空间。
>
> **规则 M3**：native 类被注册进运行时时，必须以**与宏声明相同的顺序**导出方法表，
> 使 `InvokeStatic(idx)`/`InvokeInstance(idx)` 命中正确目标。

## 3. 构造方法编号

### 3.1 编译器 / VM 逻辑

- `codegen.rs` 生成对象构造时固定发 `InvokeConstructor(0)`（第 860 行）与
  `DoConstruct(0)`——当前**只支持 0 号构造方法**，未按参数表选择重载。
- `vm.rs::InvokeConstructor(ctor_id)`（第 1124 行）通过
  `RuntimeClass::find_constructor(ctor_id)` 查找，构造方法表由
  `constructor_start_id`（=0）+ `constructor_impls`（按声明顺序注册）确定。

### 3.2 宏对齐规则

> **规则 C1**：native 类构造方法按声明顺序编号 0,1,2…，`constructor_start_id=0`。
>
> **规则 C2**：桥接层 `do_construct(target, ctor_id)` 用 `switch(ctor_id)` 分派，
> 编号与方法表下标一致（对应 C# `DoConstruct` 的 `switch(constructorId)`）。
>
> **规则 C3（限制）**：当前编译器只会发 `InvokeConstructor(0)`，示范类应保证
> **0 号构造方法**是最常用/默认的那个（`Vector2` 的 `(x, y)` 构造建议放 0 号或
> 同时提供，端到端测试以 0 号为准）。重载选择留待编译器后续增强。

## 4. 字段 index（关键差异）

### 4.1 两侧机制

**C# 参考（`AutoGenerated/Vector2.cs`）**：字段按**值类型分组**计数。
`x`, `y` 都是 float → `x` index=0，`y` index=1（float 组内下标）；
`fieldIndexCount` = `TypeCount(float=2)`；读写用 `GetFloatField(0/1)`。

**Rust 编译器（`compiler.rs::pass3_declare_field`，第 557-618 行）**：

```rust
let mut field_offset = 0usize;      // 全类型共享的单一计数器
// 每个非静态字段：
self.symbol_table.allocate_field_offset(field_id, *field_offset);
*field_offset += 1;                 // 不区分类型，统一 +1
```

即 Rust 侧字段 offset 是**全类型统一递增**（第 1 个字段=0，第 2 个=1，无论类型）。

而字段读写 IR（`codegen.rs::load_field_op`）却按值类型选择操作码
`LoadFloatField(idx)` / `LoadIntField(idx)`……

**运行期**（`object.rs::RuntimeObject`）字段值存在 `FixedFieldValuePool` 里，
按**类型分离**存储（int/float/bool/string/object 各一个 `Vec`），
`get_float_field(index)` 用 `index` 直接索引 float 组。

### 4.2 一致性分析

- 当 **同类型字段的声明顺序恰好从 0 连续** 时，Rust 的“统一 offset”与“类型分组 index”
  巧合一致（如 `Vector2` 只有两个 float，offset 0/1 == float 组 0/1）。
- 但当类**混合多种类型字段**时，两者**不一致**。例如字段顺序 `int a; float b; int c;`：
  - Rust 统一 offset：a=0, b=1, c=2
  - 类型分组 index：a(int)=0, b(float)=0, c(int)=1
  - `LoadIntField(2)`（c 的统一 offset）会去 int 组索引 2 → **越界/错值**。
- 这是编译器现存的**潜在缺陷**，但对纯 float 的示范类不触发。

### 4.3 宏对齐规则

> **规则 F1（示范类范围内）**：`Math`（无字段）、`Vector2`（仅 2 个 float 字段）
> 场景下，统一 offset 与类型分组 index 一致。宏对 `Vector2` 生成
> `get_float_field(0)=x`、`get_float_field(1)=y`，与编译器 `LoadFloatField(0/1)` 对齐。
>
> **规则 F2（通用正确做法，宏内部采用）**：宏应按 **C# 的“类型分组 index”** 为字段
> 生成读写分派（每个值类型独立从 0 计数），并同时导出 `field_type_count`（各类型计数）。
> 这样当编译器字段 index 逻辑修正为“类型分组”后，宏无需改动即可对齐。
>
> **规则 F3（记录待办）**：编译器 `pass3_declare_field` 的“统一 offset”应改为
> “按类型分组计数”，以匹配 `FixedFieldValuePool` 的类型分离存储。此项列入
> Phase A 之外的编译器修正 backlog（不阻塞本轮示范类，但混合类型字段的类必须修）。

## 5. Injector 字段编号

### 5.1 两侧机制

**C#（`AutoGenerated/Vector2.cs` 的 `SpecificInjector`）**：injector 字段同样**按值类型分组**
（`x` float:0, `y` float:1），`SetInjectorFloat(index)` 用类型组内下标；
默认值用独立的 `defaultValueIndex`，经 `GetInjectorFloatDefaultValue(index)` 取。

**Rust（`injector.rs::RuntimeInjector`）**：字段**按类型分离**存储
（`int_fields`/`float_fields`/…），`set_injector_float(index)` 用 float 组下标，
每字段存 `(值, 是否默认)`。与 C# 的类型分组一致。

**编译器收集**（`compiler.rs`，第 574-592 行）：injector 字段从
`decl.injector.fields` 按声明顺序收集为 `InjectorFieldDef { name, value_type, has_default }`，
`from_defs`（`injector.rs`）再**按 value_type 分桶**、组内顺序分配 index。

### 5.2 宏对齐规则

> **规则 I1**：native 类的 injector 字段按值类型分组、组内按声明顺序从 0 编号，
> 与 `RuntimeInjector::from_defs` 的分桶顺序一致。
>
> **规则 I2**：宏为每个 injector 字段生成 `(value, is_default)` 语义的 set/get 分派
> （对应 C# 的 `Tuple<T,bool>`），默认值走类的 `get_injector_*_default` 方法。
>
> **规则 I3**：`Vector2` 的 injector 字段 `x`/`y` 为 float 组 0/1，默认值均为 0.0，
> 与 C# `InjectorFieldDefaultValue_x/y` 对齐。

## 6. 命名空间与类型全名

- C# native 类通过 `GorgeType.Object(name, namespace, generics)` 携带命名空间，
  全名形如 `GorgeFramework.Vector2`。
- Rust `GorgeType::class(name, namespace)` 亦支持命名空间，`full_name()` 产出
  `命名空间.类名`。
- 谱面 / 源码引用 native 类用全名（如 `GorgeFramework.Math.Sqrt`）。

> **规则 N1**：宏的 `#[gorge_native_class(namespace = "GorgeFramework")]` 必须把
> 命名空间写入 `ClassDeclaration.class_type`，保证 `full_name()` 与源码引用、
> 运行时注册键（`GorgeRuntime.classes` 的 key）一致。

## 7. 参数池（InvokeParameterPool）约定

桥接层与 VM 交换数据全部经 `param_pool`：

- 入参：VM 在 `Invoke*` 前把实参写入 `set_*_param(index, value)`，`index` = 参数
  在方法签名中的**位置序**（`codegen.rs` 中 `self.param_index` 从 0 递增，
  **不区分类型**——见 §7.1 注意点）。
- 出参：桥接层把返回值写入 `set_*_return(value)`，VM 用 `get_*_return()` 取回。
- Injector：构造方法经专用位传递（C# `InvokeParameterPool.Injector`；Rust 需在
  Phase A 补 `current_injector` / 专用位，见 Phase A 任务 A4）。

### 7.1 注意点：参数 index 的类型分组

`codegen.rs::generate_method_call`（第 618-645 行）中 `param_index` 是**全类型统一递增**：

```rust
self.param_index = 0;
for arg in arguments {
    let param_addr = Address::new(ValueType::Int, self.param_index);
    self.param_index += 1;   // 不区分类型
    // Set{Type}Parameter(arg, param_addr)
}
```

但 C# native 桥接读参数用**类型分组下标**（`InvokeParameterPool.Float[0]`,
`InvokeParameterPool.Object[0/1]`——见 `AutoGenerated/Vector2.cs` 第 321-333 行，
`Scale` 的两个 object 参数用 `Object[0]`、`Object[1]`）。

> **规则 P1（关键）**：Rust 编译器目前把**所有参数**用统一递增 index 写入，
> 但 `SetFloatParameter` 实际写的是 `float_params[index]`（`param_pool.rs` 中
> `set_float_param` 按 float 数组存）。因此对**单一类型参数**的方法（如 `Math.Sqrt(float)`、
> `Vector2.distance(Vector2, Vector2)`——后者两个参数同为 object）能自洽；
> **混合类型参数**的方法会错位（与 §4 字段问题同源）。
>
> 示范类 `Math`（全 float 参数）、`Vector2`（`distance` 全 object、`lerp` 为
> `Vector2,Vector2,float` **混合**）中，`lerp` 会触发此问题。
>
> **对齐决策**：示范类端到端测试**优先选用单一类型参数的方法**（`Math.Sqrt`、
> `Vector2.distance`、`new Vector2(x,y)`）。`lerp` 等混合参数方法的桥接按 C# 类型分组
> 语义生成（宏内部正确），但端到端验证等编译器参数 index 修正后再纳入。此项与 §4.3
> 一并列入编译器修正 backlog。

## 8. 对宏（GorgeMacros）的最终约束清单

1. **M1–M3**：方法（静态+实例）单一混合编号空间，`switch(method_id)` 分派，顺序=声明序。
2. **C1–C3**：构造方法从 0 编号，示范类保证 0 号可用。
3. **F1–F2**：字段读写按**类型分组 index** 生成（宏内部正确做法），示范类 float 场景与
   编译器统一 offset 巧合一致；导出 `field_type_count`。
4. **I1–I3**：injector 字段类型分组编号，`(value, is_default)` 语义，默认值走类方法。
5. **N1**：命名空间写入 `class_type`，全名一致。
6. **P1**：桥接读参数用类型分组下标；端到端测试先用单一类型参数方法。

## 10. 关于 B-4（native 类导入）的说明

Phase C 端到端要求 `.g` 源码能引用 `GorgeFramework.Math` 等 native 类。当前
`GorgeCompiler` 的符号表**没有从外部注入 native 类声明的入口**。可选方案：
1. 在 `Compiler` 中预注册一批 native `ClassDeclaration`（来自 GorgeFramework 导出的元数据）；
2. 或提供 `.gd`/`.g` 形式的 native 类“存根声明”供编译器 Pass 1-3 收集。

此决策在 Phase C 启动前单独与用户确认，不在 Step 0 敲定。
